# 교내 개발 동아리 행사·회비 관리 웹앱 기획서

> 문서 상태: MVP 구현 기준 v1.0 (2026-09-02)
> 기술 스택: React + Spring Boot  
> 대상: 동아리원, 운영진(행사 담당자·총무)

구현 및 운영 준비 상태는 [개발 계획서](./development-plan.md), 실제 서버 구성은 [운영 배포 가이드](./deployment-guide.md)를 기준으로 관리한다.

## 1. 서비스 개요

교내 개발 동아리의 행사 공지, 참가 신청, 참가비 및 정기 회비 납부 현황을 한곳에서 관리하는 내부용 웹앱이다.

동아리원은 카카오 계정으로 로그인한 뒤 행사를 확인하고 참가 신청과 송금 완료 신고를 할 수 있다. 운영진은 행사와 회비 납부 회차를 생성하고, 신청자 및 납부 상태를 확인·확정한다.

사업자 등록 및 PG 연동 없이 운영하는 것을 전제로 한다. 실제 송금은 카카오페이 코드송금 받기 링크 또는 총무 계좌로 진행하며, 시스템은 금융기관의 입금 결과를 자동으로 조회하지 않는다. 따라서 동아리원이 먼저 `송금했어요`를 신고하고, 운영진이 계좌 내역을 대조해 최종 확정한다.

## 2. 목표와 범위

### 2.1 핵심 목표

- 행사 공지와 참가자 명단을 일원화한다.
- 참가비와 정기 회비의 미납·확인 대기·납부 완료 상태를 명확하게 관리한다.
- 동아리원이 계좌번호와 금액을 다시 입력하는 불편을 줄인다.
- 운영진의 수기 명단 대조와 반복 안내를 줄인다.
- 회비 및 행사비 변경 이력을 남겨 총무 업무의 투명성을 높인다.

### 2.2 MVP 포함 범위

- 카카오 OAuth 또는 로컬 아이디·비밀번호 인증
- 최초 로그인 시 파트 및 이름 설정
- 운영진의 신규 동아리원 승인
- 행사 목록·상세 조회 및 참가 신청/취소
- 카카오페이 코드송금 링크 및 계좌정보 제공
- 동아리원의 송금 완료 신고
- 운영진의 참가·납부 상태 확인 및 확정/반려
- 정기 회비 회차 생성 및 개인별 납부 상태 관리
- 운영진 대시보드와 기본 검색/필터
- 주요 변경 이력 저장

### 2.3 MVP 제외 범위

- PG 결제, 카드 결제, 자동이체
- 금융기관 입금 내역 자동 조회
- 자동 환불
- 행사 좌석 배정 및 복잡한 대기열
- 동아리 회계장부 전체 기능(지출결의, 영수증 OCR 등)
- 푸시 알림 및 카카오 알림톡 자동 발송
- 복수 동아리 지원

## 3. 사용자와 권한

### 3.1 역할

| 역할 | 주요 권한 |
|---|---|
| 동아리원 `MEMBER` | 행사·회비 조회, 참가 신청/취소, 송금 정보 확인, 송금 완료 신고 |
| 운영진 `STAFF` | 동아리원 기능 전체, 행사 생성·수정·마감, 참가자·납부 상태 관리, 회비 회차 관리 |
| 최고 관리자 `ADMIN` | 운영진 권한 전체, 가입 승인, 권한 변경, 공용 송금정보 설정 |

운영진 권한은 사용자가 직접 선택할 수 없고 `ADMIN`만 부여할 수 있어야 한다.

### 3.2 회원 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 로그인 계정 생성 후 온보딩을 완료했지만 운영진 승인 전 |
| `ACTIVE` | 승인된 동아리원 |
| `SUSPENDED` | 활동 정지 또는 접근 제한 |
| `WITHDRAWN` | 탈퇴 처리됨 |

로그인 방식만으로 실제 동아리원임을 확인할 수 없으므로 신규 사용자는 운영진 승인 전까지 행사 상세, 계좌번호, 명단을 볼 수 없도록 한다.

## 4. 핵심 사용자 흐름

### 4.1 최초 가입 및 온보딩

1. 사용자가 카카오 로그인 또는 로컬 회원가입·로그인을 선택한다.
2. 카카오는 OAuth 인증을, 로컬 계정은 아이디·비밀번호 검증을 완료한다.
3. 서버가 로그인 방식의 고유 식별자를 기준으로 회원을 조회하거나 생성한다.
4. 카카오 최초 로그인이라면 프로필 닉네임을 이름 입력란의 초기값으로 표시한다. 로컬 회원은 이름을 직접 입력한다.
5. 사용자가 파트를 선택하고 이름을 확인·수정한다.
6. 최종 표시 닉네임을 `{파트명} {이름}` 형식으로 생성한다.
7. 가입 승인 대기 화면을 표시한다.
8. 운영진 승인 후 모든 동아리원 기능을 이용한다.

지원 파트:

- `PLAN` → Plan
- `DESIGN` → Design
- `PE_WEB` → PE(Web)
- `PE_MOBILE` → PE(Mobile)

카카오 프로필 닉네임은 실명 인증값이 아니므로 사용자 식별 키로 사용하지 않는다. 내부 식별은 카카오 사용자 고유 ID와 서비스 자체 회원 ID로 처리한다.

### 4.2 행사 참가 및 참가비 신고

1. 동아리원이 홈에서 게시 중인 행사 목록을 확인한다.
2. 행사 상세에서 일정, 장소, 설명, 신청 기한, 참가비를 확인한다.
3. `참가 신청`을 선택한다.
4. 유료 행사라면 결제 안내 영역을 표시한다.
5. 사용자는 다음 중 하나로 송금한다.
   - 카카오페이 코드송금 받기 링크 열기
   - 은행명·예금주·계좌번호 복사 후 직접 송금
6. 송금 후 `송금했어요`를 누르고 송금 수단과 송금자명을 입력한다.
7. 상태가 `확인 대기`로 변경된다.
8. 운영진이 계좌 내역을 확인해 `납부 완료` 또는 `반려`로 처리한다.

무료 행사는 참가 신청과 동시에 납부 상태를 `해당 없음`으로 처리한다.

### 4.3 정기 회비 납부

1. 운영진이 `2026년 1학기 회비`와 같은 회비 회차를 생성한다.
2. 금액, 납부 기한, 안내문과 대상 회원을 설정한다.
3. 대상 동아리원의 홈에 미납 회비 카드가 표시된다.
4. 동아리원이 송금한 뒤 `송금했어요`를 신고한다.
5. 운영진이 입금 내역을 대조해 납부를 확정한다.

### 4.4 운영진 행사 관리

1. 운영진이 행사 제목, 설명, 일정, 장소, 참가비, 신청 기한 등을 입력한다.
2. 초안으로 저장하거나 바로 게시한다.
3. 행사별 참가자 목록에서 파트, 참가 상태, 납부 상태를 확인한다.
4. 이름·파트·상태로 필터링한다.
5. 송금 신고 정보를 계좌 내역과 대조해 확정 또는 반려한다.
6. 신청을 마감하거나 행사를 취소한다.

## 5. 상태 정의

### 5.1 행사 상태

```text
DRAFT → PUBLISHED → CLOSED
                  ↘ CANCELED
```

- `DRAFT`: 운영진만 조회 가능한 초안
- `PUBLISHED`: 동아리원에게 공개 및 신청 가능
- `CLOSED`: 신청 마감 또는 행사 종료
- `CANCELED`: 취소된 행사

### 5.2 참가 상태

```text
JOINED ↔ CANCELED
```

- `JOINED`: 참가 신청 완료
- `CANCELED`: 참가 취소

행사 신청 마감 이후의 취소 허용 여부는 행사별 설정으로 둔다.

### 5.3 납부 상태

```text
UNPAID → REPORTED → CONFIRMED
                  ↘ REJECTED → REPORTED
UNPAID/REJECTED → VOID
CONFIRMED → REFUND_PENDING → REFUNDED
```

- `NOT_REQUIRED`: 무료 행사 또는 회비 면제
- `UNPAID`: 미납
- `REPORTED`: 동아리원이 송금을 신고해 운영진 확인 대기
- `CONFIRMED`: 운영진이 실제 입금을 확인
- `REJECTED`: 금액·입금자명 불일치 등으로 반려
- `VOID`: 행사 취소, 참가 취소 또는 부과 철회로 더 이상 납부할 필요가 없음
- `REFUND_PENDING`: 환불 예정
- `REFUNDED`: 운영진이 수동 환불 후 처리 완료

`송금했어요`는 입금 완료를 의미하지 않는다. 동아리원 화면에서도 `확인 대기`와 `납부 완료`를 분명히 구분한다.

## 7. 기능 요구사항

### 7.1 인증 및 회원

- Spring Security OAuth2 Client로 카카오 로그인을 처리한다.
- 로컬 회원가입은 아이디, 비밀번호, 전화번호를 입력받으며 비밀번호는 BCrypt 해시로만 저장한다.
- 로컬 아이디와 전화번호는 각각 중복을 허용하지 않는다.
- 카카오 사용자 고유 ID는 유일해야 한다.
- 프로필 닉네임 제공 동의를 받지 못한 경우 이름을 직접 입력하게 한다.
- 최종 닉네임은 파트명과 이름을 조합해 화면에서 계산한다.
- 동명이인은 허용하며 내부 ID로 구분한다.
- 운영진은 신규 가입을 승인 또는 반려할 수 있다.
- 세션 종료 및 서비스 탈퇴 흐름을 제공한다.

### 7.2 행사

- 운영진만 행사를 생성·수정·게시할 수 있다.
- 필수값: 제목, 설명, 시작 일시, 신청 마감, 참가비
- 선택값: 종료 일시, 장소, 정원, 대표 이미지, 취소 안내
- 참가비는 0원 이상의 원화 정수로 저장한다.
- 게시 이후 참가비 변경 시 기존 신청자에게 변경 사실을 명확히 표시한다.
- 납부 확정자가 존재하면 참가비를 직접 덮어쓰지 않고 변경 이력을 남기거나 변경을 제한한다.
- 정원이 설정된 경우 선착순 마감 여부를 서버 트랜잭션으로 판단한다.

### 7.3 참가 신청

- 한 회원은 한 행사에 한 개의 활성 참가 기록만 가질 수 있다.
- 중복 클릭과 네트워크 재시도에도 중복 신청이 생성되지 않아야 한다.
- 참가 신청과 취소 시각을 기록한다.
- 신청 마감 후 운영진만 상태를 변경할 수 있다.

### 7.4 송금 및 납부 관리

- 계좌번호와 금액 복사는 반드시 사용자의 버튼 클릭으로 실행한다.
- 복사 성공/실패 피드백을 제공한다.
- 카카오페이 링크는 총무가 공식 `코드송금 받기`에서 발급한 링크만 등록한다.
- 코드송금 링크에서는 금액이 자동 입력되지 않을 수 있으므로 행사비를 별도로 크게 표시하고 금액 복사 버튼을 제공한다.
- 송금 신고 시 송금자명을 필수 입력하게 한다.
- 신고 제출 전 `실제 송금을 완료했습니다` 확인을 받는다.
- 한 납부 항목에 여러 번 신고할 수 있지만 최신 신고와 이력을 모두 보존한다.
- 납부 확정·반려·환불 처리는 운영진 ID와 처리 시각을 남긴다.
- 시스템에 인터넷뱅킹 비밀번호, 계좌 인증서, 금융앱 로그인 정보 등을 저장하지 않는다.

### 7.5 회비

- 운영진은 회비명, 금액, 납부 기한, 안내문을 설정한다.
- 전체 활동 회원 또는 선택 회원을 대상으로 지정할 수 있다.
- 운영진은 면제 사유를 기록하고 `NOT_REQUIRED`로 처리할 수 있다.
- 회원은 본인 회비 상태만 볼 수 있다.
- 운영진은 회차별 납부율과 미납자 목록을 확인할 수 있다.

### 7.6 알림

MVP에서는 외부 메시지 발송 없이 앱 내부 알림 배지로 처리한다.

- 새 행사 게시
- 참가 신청 완료
- 회비 납부 요청
- 송금 신고 접수
- 납부 확정 또는 반려

향후 카카오 알림톡이나 이메일을 연동할 수 있도록 알림 이벤트 로그를 별도 저장하는 방안을 고려한다.

상세 테이블, 관계, 제약조건, 인덱스 및 Mermaid ERD는 별도 문서로 관리한다.

- [행사·회비 관리 웹앱 ERD 설계서](./erd.md)

- 행사 참가비와 정기 회비는 `payment_obligations`에서 공통 관리한다.
- 송금 신고와 실제 납부 확정을 분리해 개인 신고만으로 납부가 완료되지 않도록 한다.
- 과거 납부 항목은 생성 당시 송금정보 버전을 참조해 총무 계좌 변경 후에도 이력을 보존한다.

상세 엔드포인트, 요청·응답 DTO, 인증·권한, 오류 코드, 상태 전이 및 동시성 정책은 별도 문서로 관리한다.

- [행사·회비 관리 웹앱 API 명세서](./api-spec.md)

- 인증: Spring Security 카카오 OAuth + 서버 세션 쿠키
- 주요 영역: 내 정보, 행사·참가, 납부 신고, 알림, 회원 관리, 행사 관리, 회비 관리, 납부 확정·반려·환불, 송금정보, 감사 로그
- 상태 변경 API는 서버 권한 검사, 허용 상태 검증, 낙관적 잠금 및 감사 이력을 적용한다.
- 일반 동아리원은 본인의 참가·납부 데이터만 조회할 수 있다.

## 10. 기술 구성

### 10.1 프론트엔드

- React + TypeScript
- Vite
- React Router
- TanStack Query: 서버 상태 조회·캐시·재요청
- React Hook Form + Zod: 입력 폼과 클라이언트 검증
- UI 라이브러리는 팀 합의 후 선정
- 모바일 우선 반응형 UI

### 10.2 백엔드

- Java 21
- Spring Boot 3
- Spring Security + OAuth2 Client
- Spring Data JPA
- PostgreSQL
- Flyway: 데이터베이스 마이그레이션
- Bean Validation
- OpenAPI/Swagger: API 명세 및 테스트

### 10.3 권장 배포 구조

```text
사용자 모바일 브라우저
        ↓ HTTPS
React 정적 파일 + /api 리버스 프록시
        ↓
Spring Boot API
        ↓
PostgreSQL
```

프론트와 API를 같은 사이트 출처로 제공하면 OAuth 리다이렉트, 쿠키, CORS 및 CSRF 구성이 단순해진다.

### 10.4 인증 방식 권장안

- Spring 서버가 카카오 OAuth Authorization Code 흐름을 담당한다.
- 로그인 완료 후 서버 세션을 생성한다.
- 세션 ID는 `HttpOnly`, `Secure`, 적절한 `SameSite` 속성의 쿠키로 전달한다.
- 프론트엔드 JavaScript가 카카오 액세스 토큰을 직접 보관하지 않는다.
- 관리자 API는 URL 분리뿐 아니라 서버 측 역할 검사로 보호한다.

## 11. 보안·개인정보 원칙

- 계좌번호와 행사 정보는 승인된 회원에게만 노출한다.
- 카카오 사용자 고유 ID, 이름, 파트는 개인정보 처리방침과 탈퇴 정책에 포함한다.
- 꼭 필요한 카카오 동의 항목만 요청한다.
- 행사 설명을 Markdown 또는 HTML로 받는다면 저장·출력 시 XSS 방지 처리를 한다.
- 모든 상태 변경 API에 인증·인가와 서버 측 입력 검증을 적용한다.
- 금액은 클라이언트가 보낸 값을 신뢰하지 않고 서버에 저장된 청구 금액을 사용한다.
- 납부 확정과 권한 변경을 감사 로그에 남긴다.
- 로그에 세션 쿠키, OAuth 토큰, 전체 계좌번호를 남기지 않는다.
- 송금 증빙 이미지는 MVP에서 수집하지 않는다. 필요해질 경우 계좌·잔액 등 불필요한 금융정보 노출 위험과 보관 기간을 먼저 설계한다.
- 계좌정보 변경 권한은 최소 인원에게만 부여한다.

## 12. 주요 예외 상황

- 카카오 프로필 닉네임 제공 동의를 하지 않은 사용자
- 동일한 이름과 파트를 가진 회원이 여러 명인 경우
- 신청 버튼 중복 클릭 또는 네트워크 재시도
- 정원 마지막 한 자리에 여러 사용자가 동시에 신청하는 경우
- 참가 신청 전 또는 신청 취소 후 송금한 경우
- 참가비보다 적거나 많은 금액을 송금한 경우
- 본인이 아닌 가족·친구 이름으로 송금한 경우
- `송금했어요`만 누르고 실제 송금하지 않은 경우
- 운영진이 같은 신고를 동시에 처리하는 경우
- 납부 확정 후 행사 참가비가 변경되는 경우
- 행사 취소 후 수동 환불이 필요한 경우
- 총무 계좌 또는 카카오페이 송금 링크가 변경되는 경우
- 카카오 계정 연결 해제 또는 서비스 탈퇴 후 과거 회계 기록을 보존해야 하는 경우

동시 처리 문제에는 낙관적 잠금 또는 상태 조건부 업데이트를 적용한다. 예를 들어 `REPORTED` 상태인 건만 `CONFIRMED`로 변경할 수 있도록 한다.

## 13. 운영 정책 초안

- 참가비와 회비는 운영진 확인 전까지 `납부 완료`로 표시하지 않는다.
- 운영진은 반려 시 사유를 작성한다.
- 환불은 실제 계좌 송금 후 시스템 상태를 변경한다.
- 금액 변경, 납부 확정, 환불, 권한 변경 기록은 삭제하지 않는다.
- 참가자 명단과 납부 현황을 일반 동아리원끼리 공개하지 않는다.
- 카카오페이 코드송금 받기 기능은 비사업적 개인 간 송금·정산 범위에서 사용하고, 정책 변경 시 계좌 직접송금만 제공할 수 있도록 기능을 분리한다.

## 15. 테스트 기준

### 필수 시나리오

- 신규 사용자가 카카오 로그인 후 온보딩을 완료하고 승인 대기 상태가 된다.
- 미승인 사용자는 행사 상세와 계좌정보에 접근하지 못한다.
- 승인된 회원은 행사에 한 번만 신청할 수 있다.
- 유료 행사 신청 시 정확한 금액의 납부 항목이 생성된다.
- `송금했어요` 신고만으로 납부 완료가 되지 않는다.
- 운영진이 확정했을 때만 `CONFIRMED`가 된다.
- 반려된 회원이 다시 신고할 수 있다.
- 회비 대상자에게만 회비 납부 항목이 표시된다.
- 일반 회원이 운영진 API를 호출하면 `403`을 받는다.
- 행사비 확정 이후 잘못된 금액 변경이 차단된다.
- 동일 요청 재전송에도 참가·납부 데이터가 중복 생성되지 않는다.

## 18. 구현 전 확정할 사항

1. 신규 회원 승인 방식: 운영진 승인만 사용할지, 초대코드를 함께 사용할지
2. 이름 및 파트 변경을 즉시 허용할지, 운영진 승인을 받을지
3. 행사 신청 취소 가능 시점과 참가비 환불 기준
4. 행사 정원 초과 시 단순 마감할지, 대기자를 받을지
5. 회비 대상자를 전체 활동 회원으로 자동 지정할지, 매번 선택할지
6. 송금정보를 모든 행사에서 공통으로 사용할지, 행사별로 덮어쓸 수 있게 할지
7. 운영진 역할을 `행사 담당자`와 `총무`로 더 세분화할지
8. 탈퇴 회원의 참가·납부 기록 보존 기간
